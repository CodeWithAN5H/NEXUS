# NEXUS — v0.2.0-alpha Implementation Plan

**Status:** milestones **2.1a, 2.1b, 2.2a and 2.1c are implemented** in
`v0.2.0-alpha.1` (2026-11-19); the release itself waits on the signing keystore.
2.2b–2.5b are not started. This document refines
[ROADMAP.md](../ROADMAP.md) §v0.2 into milestones small enough to finish, review,
test and release one at a time. Where this document and the roadmap disagree about
*what* v0.2 contains, the roadmap wins; this document only decides *in which
order* and *how it is proven*.

## 2. Milestones

### 2.1a — Contract and descriptor foundation ✅ implemented

**Goal:** the new provider contract exists and is honest, with no user-visible
change.

- `ProviderKind`, `ProviderDescriptor` envelope (id, name, version,
  `contractVersion`, kind, capabilities, configuration fields, attribution,
  origin), `ProviderContract.current`.
- Three axis types plus the derived presentation state; compatibility evaluated
  once at registration.
- `ProviderFailure` sealed hierarchy mapped to `AppFailure`.
- `probe()` returning a timestamped snapshot replaces the synchronous `status`;
  mandatory `dispose()`.
- The existing sample provider is migrated and keeps behaving exactly as it does
  today (`match()` → `null`, `limited`, `isSample`).

**Depends on:** nothing.
**Tests:** T-A01–T-A08; all 79 existing tests still green.
**Done when:** analyze clean, formatting clean, suite green, `Sources` still works
against the migrated contract, and a new provider can be added by appending one
class (proven by the sample provider's own migration with no screen change).
**Release:** no APK (no user-visible change).

### 2.1b — Metadata behind the interface ✅ implemented

**Goal:** AniList stops being a special case.

- `MetadataProvider` + `MetadataCapability`; `AniListMetadataProvider` wraps the
  existing client; `MetadataRepository` depends on the interface.
- `MetadataRegistry`; metadata is registered in the same bootstrap file as
  streaming providers (two lists, one file).
- Metadata works with zero streaming providers installed — asserted, not assumed.

**Depends on:** 2.1a.
**Tests:** T-A09, T-A10; existing metadata/model tests unchanged.
**Done when:** no file outside `lib/integrations/anilist/` imports
`AniListClient`; discovery, details, library and history behave identically.
**Risk:** `MetadataRepository`'s TTL cache moves or is duplicated — decide once
(keep it in the repository, above the interface).
**Release:** no APK.

### 2.2a — Provider store and additive schema v2 ✅ implemented

**Goal:** provider state can be persisted before anything writes to it.
The migration test runs against the committed `test/fixtures/nexus_v1.sqlite`.

- Drift schema 1 → 2 (additive only): `provider_entries`, `provider_title_prefs`,
  `provider_manifests` as specified in [DATABASE.md](../DATABASE.md) §6.
- `ProviderStore` (repository) + Riverpod wiring; backfill from `sources.enabled`.
- `sources.enabled` stays readable for this release; defaults preserved.

**Depends on:** 2.1a.
**Tests:** T-P01–T-P05, T-P11.
**Done when:** an existing v1 database upgrades with every row intact and
`PRAGMA foreign_keys` still on; a fresh install and an upgraded install behave
identically.
**Risk:** Drift migration mistakes are unrecoverable for testers — the migration
test must run against a committed v1 fixture file, not a freshly created one.
**Release:** no APK (invisible).

### 2.1c — Resolution, priority and per-title preference ✅ implemented

**Goal:** every matching provider is usable, in the user's order.
The reorder control itself is 2.2d; priority is stored, resolved and tested here.

- `ProviderResolver` collects all matches, honours stored priority, records
  per-title preference, keeps per-provider failures.
- Candidate filter: installed ∩ enabled ∩ compatible ∩ configured ∩
  `seriesMatching`; probe concurrency capped at 4.
- Episodes tab shows a collapsible source-error line; a stale resume hint
  re-resolves instead of failing.

**Depends on:** 2.1a, 2.2a (priority and preference need the store), 2.1b (the
resolver matches against metadata titles).
**Tests:** T-R01–T-R04, T-R07–T-R15.
**Done when:** two fake providers matching one title both appear, reordering them
survives a restart, and one failing provider never empties the screen.
**Release:** first `v0.2.0-alpha.1` pre-release APK (user-visible: source list
behaviour changed).

### 2.2b — Manifest validator and interpreter ✅ implemented

**Goal:** a compatible manifest can be validated and served without a new APK.
The validator, JSON path reader, template binder, `ManifestHttp` and
`ManifestStreamingProvider` are implemented and tested against hermetic fixtures;
the install/configure/remove flow is 2.2c by design.

- Model + validator for [PROVIDER_MANIFEST.md](PROVIDER_MANIFEST.md) (parse →
  schema → templates → paths → semantics → compatibility).
- JSON path reader, template binder, hardened header builder.
- `ManifestHttp`: allowlist on parsed URIs, manual redirects, decoded-byte cap,
  pacing, timeouts, one retry for idempotent GETs.
- `ManifestStreamingProvider implements StreamingProvider` — indistinguishable
  from a built-in adapter at the resolver.
- Media URL validator (scheme, `mediaHosts`, length) before any URL reaches the
  player.

**Depends on:** 2.1a (contract), 2.2a (storage), 2.1c (resolver to plug into).
**Tests:** T-M01–T-M24 and T-B01–T-B45; security tests S1, S2, S4, S5, S7.
**Done when:** the two committed valid examples install and serve from fixtures;
every committed invalid example is refused with the documented code and path; no
manifest can produce a network request outside its allowlist.
**Risk:** this is the largest milestone. If it slips, it slips *after* 2.1c — the
platform release does not wait for it.
**Owner decision:** D2 (is Tier B in v0.2 at all?) gates the start.

### 2.2c — Provider lifecycle and configuration (implemented 2026-11-19)

**Goal:** install, configure, enable, prioritise and remove are real, and secrets
are safe.

**Delivered:** paste-import with a review card and every validation error; a
generated configuration form for all documented field types; keystore-backed
secrets with install/update rollback; stored-manifest revalidation at startup and
before every provider is built; enable/disable with disposal; removal that keeps
library, history, positions and preferences; and the Sources cards that expose
all of it. Priority ordering, the full six-state action set and diagnostics
export remain in 2.2d, which is why the completion note below is scoped to the
lifecycle rather than the whole Sources surface.

- Lifecycle commands on the store, with `dispose()` on disable/remove.
- Generated configuration form from declared fields; validation; keystore-backed
  secrets (`flutter_secure_storage` — decision D4); configuration state
  (`notRequired`/`incomplete`/`configured`/`rejected`).
- Manifest re-validation on load; a corrupt row disables only its provider.
- Remove deletes its rows, manifest and secrets, and nothing else.

**Depends on:** 2.2a, 2.2b.
**Tests:** T-B46, T-P06–T-P10, T-R05, T-R06, T-S04–T-S08.
**Done when:** disabling keeps configuration; removing leaves library, history and
positions byte-identical; no secret exists outside the keystore. ✅ Verified by
`provider_lifecycle_test.dart` (disable/re-enable, removal with user data intact,
secret absence from every SQLite column) and `provider_sources_ui_test.dart`.
**Risk:** secrets on Windows — verify the plugin works there before claiming
parity (2.5a).
**Release:** `v0.2.0-alpha.2` once visible in Sources.

### 2.2d — Sources surface, states and diagnostics

**Goal:** the three axes are visible and actionable, without a redesign.

- Derived state chips per [UI_SPEC.md](../UI_SPEC.md) §4.8; one action per state.
- Import review screen (id, origin, capabilities, hosts, validation result).
- Per-provider diagnostics, opt-in, redacted, cleared on remove.
- Priority ordering control; empty state explains user-supplied sources.

**Depends on:** 2.2c.
**Tests:** T-S01–T-S09.
**Done when:** each of the six derived states renders with the correct
action, and an invalid manifest produces paths and codes, not a stack trace.
**Note:** this is the only milestone that changes screens; it reuses existing
tokens and components. No visual redesign (see task restriction in
`PROJECT_STATUS.md`).

### 2.3a — Authorised content provider

**Goal:** real content, through either tier.

- The owner's authorised provider, implemented as a Tier A adapter **or** as a
  manifest, whichever fits the source's API.
- Filled review checklist; attribution; honest capabilities.
- The sample provider stays available and labelled; it is not silently replaced.

**Depends on:** 2.2b (if manifest) or 2.1a only (if built-in).
**Blocked by:** D1 — owner must choose the authorised provider.
**Tests:** T-A01–T-A08 for the new adapter, or the manifest suite against a
recorded fixture set.
**Done when:** a real title resolves to real episodes in the app, attributed.
**Release:** `v0.2.0-alpha.3`.

### 2.3b — Real episodes and subtitles

**Goal:** the Episodes tab and the player's track menus tell the truth.

- Real episode lists replace the "no source available" state for matched titles.
- Provider subtitles appear with language labels; a provider without them says so.
- Absolute-number merging with AniList episode counts; "next episode" works.
- Stream failures (expired token, geo, offline) surface with actionable copy.

**Depends on:** 2.3a.
**Tests:** T-B17–T-B29 plus manual verification on a device (D6).
**Done when:** playing episode *n*, finishing it, and auto-advancing to *n+1* all
work for a real title, with progress persisted.
**Release:** `v0.2.0-alpha.4`.

### 2.4a — Explore pagination

- Cursor/page paging for Explore and rails with a visible end state; no duplicate
  items on refresh; scroll position preserved.
- **Depends on:** nothing (parallel to 2.2).
- **Tests:** repository-level paging test + widget test for append/end-of-list.
- **Release:** batched with the next pre-release.

### 2.4b — AniList episode metadata

- `streamingEpisodes` and air dates merged into the Episodes tab by absolute
  number; provider episodes win on conflict, AniList fills gaps.
- **Depends on:** 2.3b.
- **Tests:** merge test with three fixtures (provider-only, AniList-only, both),
  including numbering conflicts.
- **Release:** batched.

### 2.5a — Windows build verification

- `flutter build windows` on a Windows host (MSVC + C++ workload), provider
  management at desktop width, keyboard paths, keystore on Windows.
- **Depends on:** 2.2d.
- **Blocked by:** D5 — Windows host access. Until then this stays unverified, and
  `PROJECT_STATUS.md` must keep saying so.
- **Done when:** the built binary launches, Sources works with the manifest tier,
  and the verification is recorded with versions and dates.

### 2.5b — Launcher icon and splash

- Adaptive icon (foreground/background/monochrome) and an Android 12+ splash
  derived from the brand mark; no new visual identity.
- **Depends on:** nothing; needs the brand asset decision.
- **Tests:** build + inspect generated resources (`aapt2 dump badging` for the
  label, presence of `mipmap-anydpi-v26`), not a screenshot review.
- **Release:** batched.

## 4. Definition of done (every milestone)

1. `dart format --output=none --set-exit-if-changed lib test` clean.
2. `flutter analyze` — no issues.
3. `flutter test` — all green, with the new matrix IDs referenced in the test
   names (`test('T-B21 …')`) so the matrix and the suite stay linked.
4. Documentation updated in the same commit: `CHANGELOG.md`, `PROJECT_STATUS.md`,
   and whichever spec the change touched.
5. Commit and push to `main` with the milestone in the subject.
6. If user-visible: release-signed APK built, `aapt2` package/version checked,
   `apksigner` certificate checked, checksum published — and only then a GitHub
   Release with the APK and `SHA256SUMS.txt`.
7. `PROJECT_STATUS.md` says what was verified and what was not. "Built" is never
   reported as "tested".

For v0.2 the application id (`app.nexus`), the signing identity and the data
directory stay unchanged, so every update is an in-place upgrade over the previous
APK. A version code bump per release is mandatory.

Decisions D1 and D2 are the only ones that change what v0.2 *is*. The rest change

## 6. What is explicitly not in v0.2

So the milestone cannot quietly grow:

- Metadata manifests, OAuth-based provider auth, GraphQL manifests, DRM any kind
  (see [PROVIDER_MANIFEST.md](PROVIDER_MANIFEST.md) §12).
- Offline downloads, PiP, per-title quality memory, buffering reports (v0.3).
- AniList account, sync, scores (v0.4).
- A provider directory, remote manifest feed, or "install from link" without a
  review screen.
- Any redesign of Home, Explore, Details, Library, History, Profile or Player.
